# Code audit — 2026-10-11

Read-only audit of the whole repository: 7 areas (retrieval core, services, UI,
security/privacy, data pipeline, tests/evaluation, ops/performance), each reviewed by one
agent and then checked by a second agent trying to refute every finding. 63 findings, none
refuted. The security area's verifier returned no verdicts, so its six findings were
checked by hand (marked "by hand" in the appendix). Nothing was changed.

Companion: `docs/plan-source-scaffolding-2026-10-11.md` (sources and hieroglyphs on the
cards, the Camilla work).

## What is healthy

- **The private St Andrews boundary holds.** No St Andrews rows in the committed tree, git
  history or LFS; unkeyed sessions only ever get public data; caches are keyed per corpus;
  every `unsafe_allow_html` block escapes its text.
- **Test suite:** 675 passed, 1 skipped, 0 failed (7.5 min, scratch venv). The reviewer
  gate is tested end to end.
- **Scoring code** (scorer, tokens, tfidf) is consistent: fast and slow paths agree, empty
  input is guarded, 200k random fuzz inputs found no mismatch.
- Corpus loads once per process, not per visitor; backups use SQLite's online backup and
  an integrity check, and go off-site.

### 1. Licence and attribution (owed to rights holders now)

  says they are not in the corpus. Add the `tla-demotic-v18-premium` citation to

- The reviewed-annotations export credits **every** row to TLA Earlier Egyptian,
  including AES, BBAW and Ramses rows. Build the licence column per row from `source`.

### 2. Broken for users right now
- **"Prepare CSV export" always crashes** (`with_licence_notice` never imported) and shows
  a traceback to the public.
- **A non-ASCII reviewer key crashes the unlock** with a traceback (`compare_digest` on
  str). Compare UTF-8 bytes; set `showErrorDetails = "none"` for the public site.
- **Corpus text goes through Markdown**: editor brackets like `[r](m)` become links,
  `$…$` becomes LaTeX. Escape before `st.markdown`. Same root cause lets a `?q=` link
  inject an image into the "No parallel" warning.

### 3. The tool presenting guesses as evidence (its core promise)
- **Auto stage detection calls hieroglyph pastes "Demotic"** (47 of 200 held-out Earlier
  Egyptian sentences); the guard meant to stop it never fires, because Demotic has no
  hieroglyph rows of its own.
- **Confidence never drops below ~0.4–0.5**, even when the evidence is one shared group
  out of ten: confidence is relative to the query's own best row.
- A stage that has never seen a sign group can outscore one that has (unreadable groups
  cost nothing).

### 4. Deploy and backup safety (the annotations DB is the only irreplaceable file)
- A deploy reports **"healthy" when the app crashes for every visitor** (health check +
  warm-up don't look for exceptions).
- A failed deploy leaves new code on disk with **no rollback**.
- Backups check for corruption but **not that the annotations are still there**; after 30
  days every good copy can be gone.
- Annotation saving is **open to anyone if `REVIEWER_KEY` is empty** (fail-open);
  no limit on key guesses.

### 5. Search-key bugs (one batch, one PR, with tests)
All in `app/data/normalizer.py`, all measured on the real corpus: capital H̱ vanishes
(408 rows); `ʾ` deleted so rʾ "mouth/spell" becomes the preposition r (7,443 rows); typed
ʿ ȝ ỉ deleted; superfluous `{…}` text indexed as real (5,777 rows); u̯ ≠ w; bracketed plural
gives `ww`; ASCII `(i)` kept; fractions `1/2` → `12`. Plus per-stage IDF using the wrong
corpus size. Coordinate with the MdC change promised to Nederhof; it touches the same code.

### 6. Evaluation validity (affects numbers already sent to experts)
- Several v4 "hits" are **the other edition of the same sentence** (the twin guard only
  blocks overlap ≥ 0.9; COMP_001 is one), so the reported 0.90 includes free hits.
- The headline metric **can't tell the app from a plain word-overlap baseline**.
- The "held-out" set was used to choose configurations; there is **no untouched test
  set**. The reading-model eval uses a lexicon built from its own test sentences (Ramses).
- Tuning defaults to the contaminated v1 benchmark and the shipped weights can't be
  reproduced. The twin-cleanliness test checks a retired benchmark.

Before quoting any accuracy number again: twin-guard v4 at a lower threshold, report the
baseline beside it, and freeze a new test set nobody looks at.

### 7. Scripts that can destroy data when run with defaults
- `import_tla_dataset.py` with no arguments **truncates the tracked worklist to 100 rows**.
- `build_examples_from_real.py` **overwrites the 130k-row corpus with ~12.7k rows**.
- `import_ramses.py` writes into `data/private/`, which the app serves as reviewer-only rows.

### 8. Everything else
Low-severity data labels (all Ramses rows dated "New Kingdom", Demotic period labels,
lost TLA date ranges and editors, AES text name thrown away), UI papercuts, performance
(signature hashing 3–4× per rerun, cold keyed index build), and ops hygiene (systemd units
only on the friend's PC, relative DB path, unpinned transitive packages, no alerting).

### A2. [high] 11,996 TLA Demotic rows are served and committed with no attribution; DATA-LICENSE.md says they are not in the corpus
`app/ui/whyptology_app.py:213` · security-privacy · confirmed (by hand)

- **What happens:** A visitor searches a Demotic sentence. The footer credits only the TLA Earlier Egyptian and Late Egyptian corpora, never `tla-demotic-v18-premium`. Anyone reading DATA-LICENSE.md is told there are no Demotic or Ramses rows and only 5k BBAW rows. As a result the attribution and the 'indication of changes' for about 59k committed rows are missing or wrong, which is a curable licence violation under §6(b).
- **Fix:** Add the Demotic v18 dataset citation and link to CORPUS_CREDITS['TLA'] and to DATA-LICENSE.md, with its own change notes. Correct the Ramses and BBAW sections to match the current counts and the text-only import. Extend the credit test to check each distinct language_stage/source_text_id prefix under TLA.

### A3. [high] Auto stage detection picks 'Demotic' for hieroglyph pastes, and the guard that should prevent it never fires
`app/services/stage.py:483` · services · confirmed

- **What happens:** I measured this in a scratch run on held-out data: 200 corpus sentences per stage, removed from training together with every row that has the same sign string. 47 of 200 Earlier Egyptian hieroglyph sentences were classified as 'Demotic', and 24 of 200 Late Egyptian ones. Example: the paste 𓆛𓏌 𓇗 scored Demotic -7.88, Earlier -8.03, Late -8.74. On the 47 misrouted Earlier pastes, sign-reading accuracy was 0.618 with the Demotic model and 0.719 with the correct Earlier model. So a user gets a wrong stage label and about 10 points worse readings.
- **Fix:** Skip a stage unless it has its own labelled hieroglyph rows. For example, count aligned rows whose normalize_stage(language_stage) == candidate, or simply leave Demotic out of the candidates for a hieroglyph paste. Also require a real margin between the top two stages instead of 1e-9 (see the next finding).

### A4. [high] Several v4 'hits' come from another edition of the target sentence (the twin guard only blocks overlap of 0.9 or more)
`scripts/build_competitive_ambiguity_benchmark.py:58` · tests-eval · confirmed

- **What happens:** COMP_001 query 'skhr i khft pl nb sn nb b' -> the top suggestion is the other edition of the very same sentence, so the hit measures duplicate lookup, not reading. The reported 0.90 and 0.8889 therefore both include free hits.
- **Fix:** At eval time, also remove every row whose word overlap with the target is 0.7 or more (or whose notation-folded reading is identical), not just the target row. Rebuild or re-score v4 and the held-out set that way, and give each benchmark a list of its known near-twins.

### A11. [medium] A deploy reports 'healthy' even when the app crashes for every visitor
`scripts/warm_streamlit.py:119` · ops-perf · confirmed

- **What happens:** A commit has an ImportError in app/services/*.py, or a KeyError when it reads a renamed CSV column. The deploy pulls, restarts, the warm-up prints 'script finished (FINISHED_SUCCESSFULLY)', and the deploy prints 'healthy on 8502' and exits 0. Every visitor sees a red Python traceback until someone happens to open the site.
- **Fix:** In warm_streamlit.py, also watch the ForwardMsg deltas for an exception element (delta.new_element.exception) and return 1 if one arrives. Run the warm-up from the deploy script after the restart, not only from ExecStartPost, and treat a non-zero exit as a failed deploy. Use a real query that must return at least one result, then fail the deploy if it does not.

### A12. [medium] A deploy changes the code under the running app and has no rollback
`scripts/egyptology-deploy.sh:18` · ops-perf · confirmed

- **What happens:** `pip install` fails halfway through, for example a network drop on PyPI or a wheel that does not exist for this Python. The deploy stops. The old process keeps serving, but the files on disk are the new commit and the venv is a mix of old and new versions. The next time the service restarts (Restart=on-failure after a crash, the friend rebooting, or the next deploy), it starts that untested combination. If it does not come up, the site stays down until someone works out `git reset --hard <old sha>` by hand.
- **Fix:** Write BEFORE to a file such as ~/egyptology-last-good. If pip, the import, the restart or the health/warm-up check fails, run `git reset --hard $BEFORE`, run `pip install -r requirements.txt` again and restart. Better still, deploy into a new directory with its own venv and switch a symlink, so the live tree is never edited in place. Add a short 'Rollback' section to DEPLOYMENT.md.

### A13. [medium] Backups are checked for corruption, but not for whether the annotations are still in them; good copies expire after 30 days everywhere
`scripts/backup_db.sh:89` · ops-perf · confirmed

- **What happens:** A buggy migration or script, a wrong DELETE, or a rebuild that seeds a fresh database deletes or empties the annotations table. Each night's backup still says 'integrity_check ok'. If nobody notices for 31 days, the last good copy is deleted from both the box and B2, and the experts' annotations, the one irreplaceable data in the project, are gone.
- **Fix:** After the integrity check, count annotations (and examples). Exit non-zero, and keep the older snapshots, if the count drops compared with the newest existing snapshot. Keep a long-tail history, for example the first snapshot of every month forever. Turn on B2 Object Lock or lifecycle rules, and give the box a key that can upload but not delete, so neither the box nor a bad RETENTION_DAYS value can wipe the off-site copies. Rehearse a restore once a month with gzip -t, decompress, and count.

### A14. [medium] Capital H̱ (as in H̱nm.w, Khnum) folds to nothing: the whole consonant disappears from the search key
`app/data/normalizer.py:382` · retrieval-core · confirmed

- **What happens:** A user searches 'ẖnm.w' (or ASCII 'khnmw') for the god Khnum. The 245 rows indexed as 'khnmw' are found, but the BBAW rows that write the name capitalised (H̱nm.w) are indexed as 'nmw' and never come up. They show up for an unrelated query 'nmw' instead.
- **Fix:** Compose again after lowercasing in normalize_text: `value = nfc(nfc(value).lower())`. Add a test asserting search_fold('H̱nm.w') == search_fold('ẖnm.w') == 'khnmw'. Rebuild the index afterwards (mdc_norm is computed at load time, so a restart is enough).

### A15. [medium] The corpus's ʾ marker is deleted, so rʾ 'mouth/spell' becomes the preposition r and tʾ 'bread' becomes t
`app/data/normalizer.py:394` · retrieval-core · confirmed

- **What happens:** Query 'rʾ n pr.t m hrw' (the Book of the Dead spell title) is indexed as 'r n prt m hrw'. The key word 'spell' counts as the near-weightless preposition 'r', so ranking rests on the other tokens. Query 'rꜣ n pr.t m hrw' typed the Gardiner way gives 'ra n prt m hrw' and matches rows about Ra, not the 1,500+ rows that contain rʾ.
- **Fix:** In normalize_transliteration, fold ʾ (U+02BE) the same way as ꜣ (to 'a'), before normalize_mdc runs. Note it in the docstring, because the search key is deliberately lossy. Add a test that search_fold('rʾ') == search_fold('rꜣ').

### A16. [medium] Common substitute letters a user may type (ʿ ȝ ỉ) are silently deleted from the query
`app/data/normalizer.py:429` · retrieval-core · confirmed

- **What happens:** The user types 'ʿnḫ' (ankh). The search key becomes 'nkh' instead of 'ankh', which matches nothing useful. 'ȝḫ' becomes 'kh', and 'ỉr' becomes 'r' (the preposition again). The user gets weak or wrong suggestions and no sign that their characters were dropped.
- **Fix:** Add folds in normalize_transliteration: 'ʿ'→'a' (like ꜥ), 'ȝ'/'Ȝ'→'a' (like ꜣ), 'ỉ'→'i' (like ꞽ). Also consider having parse_query warn when a non-ASCII letter is deleted by the fold.

### A17. [medium] Text the editor marks as superfluous ({…}) is indexed as if it were real text
`app/data/normalizer.py:394` · retrieval-core · confirmed

- **What happens:** A BBAW row reads 'ḏd.n={f} …'. Its search key gets an extra suffix token 'f' that is not part of the reading. 'nb{.t}' is indexed as 'nbt' (feminine) instead of 'nb'. A user typing the correct reading 'nb' loses token overlap with these rows, and the extra tokens also lower their overlap scores for every query.
- **Fix:** Before folding in normalize_transliteration (or search_fold), delete each `{...}` span including its content: `re.sub(r'\{[^{}]*\}', '', value)`, run until nothing changes so nested {{…}} is handled. Keep the raw text for display. Add tests for 'nb{.t}' → 'nb' and 'ḏd.n={f}' → 'djdn'.

### A18. [medium] No rate limit, lockout or logging on reviewer-key attempts; the shared key is the only barrier to the NC rows
`app/ui/whyptology_app.py:1193` · security-privacy · plausible (depends on key strength)

- **What happens:** An attacker runs a small websocket script against https://vela-optiplex-3070.taile0409f.ts.net/ that sets the password widget and clicks Unlock in a loop, opening fresh sessions as needed. With a dictionary-word passphrase it gets in, then views or copies the 7,659 St Andrews rows (whose licence forbids redistribution) and writes annotations. No log shows thousands of failed attempts.
- **Fix:** Keep a module-level (process-wide) failure counter with a timestamp. After N failures in a window, sleep or refuse every unlock for a cooldown, and log each failure with a count (never the typed value). Document generating the key with `python -c 'import secrets; print(secrets.token_urlsafe(24))'`.

### A19. [medium] Reviewer-key check crashes on any non-ASCII input, and Streamlit shows the full traceback to the public
`app/ui/whyptology_app.py:1194` · security-privacy · confirmed (same as UI finding)

- **What happens:** A reviewer types 'Pässwort' or pastes a transliteration into the key box and clicks Unlock. The page shows a red exception box with the traceback instead of 'That key was not recognised'. If the operator ever sets a key containing a non-ASCII character, nobody can unlock at all.
- **Fix:** Compare bytes: `secrets.compare_digest(entered.encode('utf-8'), expected.encode('utf-8'))`. Also set `[client] showErrorDetails = "none"` in .streamlit/config.toml for the public deployment, so unexpected errors do not print code and paths to visitors.

### A20. [medium] Annotation writes fail open: if REVIEWER_KEY is missing, every anonymous visitor can write to the shared database
`app/ui/whyptology_app.py:1134` · security-privacy · confirmed (by hand; only when REVIEWER_KEY is empty)

- **What happens:** During key rotation the operator leaves `REVIEWER_KEY=` empty and restarts. Any internet visitor can now 'Save annotation' on any row. A spammer fills the Reviews page and the reviewed-annotations export with junk, or overwrites expert corrections with new 'latest' annotations, and no UI tells the operator the gate is off.
- **Fix:** Make writes fail closed on deployments: require an explicit opt-out such as ALLOW_OPEN_ANNOTATIONS=1 for local development, and return False when the key is empty otherwise. Alternatively refuse to start, or show a loud operator banner, when ANNOTATIONS_DURABLE=1 is set without REVIEWER_KEY.

### A21. [medium] Suggestion confidence has a floor of about 0.4–0.5, even when the evidence is almost nothing
`app/services/suggestions.py:515` · services · confirmed

- **What happens:** Checked with suggest_top_readings on a one-row pool. (a) Hieroglyph query of 10 groups whose only retrieved row shares 1 group (evidence: 'sign groups cover 10% of the query'): confidence_score = 0.513. (b) Text query 'ꞽw rḫ.n =ꞽ ḏd mdw nb ꜥnḫ wꜣs' against a row reading 'sḏm =f' (no shared token at all): confidence_score = 0.406.
- **Fix:** Do not let the pool-relative terms set the absolute level. For example, multiply the confidence by an absolute evidence term (best glyph LCS coverage, or token overlap with the query), or show the per-query relative score separately from a 'match strength' bar. Add a test that a 10%-coverage candidate cannot score above some low ceiling.

### A22. [medium] Attested sign groups longer than 10 signs are always split, even when pasted exactly as one group
`app/services/segmentation.py:346` · services · confirmed

- **What happens:** Segmenter on the full corpus model. The 18-sign group 𓃒𓂡𓉻𓇓𓇋𓇋𓏏𓏪𓎟𓇾𓇾𓇳𓄊𓁧𓈘𓇋𓏠𓈖 is attested 54× as 'wsr-mꜣꜥ.t-rꜥ-mry-ꞽmn'. Pasted as exactly that one group, it is split into ['𓃒𓂡𓉻𓇓𓇋𓇋𓏏𓏪', '𓎟𓇾𓇾', '𓇳𓄊𓁧𓈘𓇋𓏠𓈖']. The first piece is unattested and gets the borrowed reading 'kꜣ-nḫt-ꜥꜣ-nswy.t', and that split is then used for retrieval and suggestions.
- **Fix:** In segment(), also offer every span [i, j) that is exactly one pasted group, or any attested/lexicon group, no matter how long. For example, precompute the hint-delimited spans and add them as extra candidates when j - i > max_group_glyphs. Add a test that an attested 11+ sign group pasted alone comes back unchanged.

### A23. [medium] The headline accuracy metric cannot tell the app apart from a trivial word-overlap baseline
`scripts/run_competitive_ambiguity_eval.py:185` · tests-eval · confirmed

- **What happens:** Someone changes the ranker in a way that makes it worse for real Egyptologists, but the new top-3 still shares a quarter of its words with the query. Top-3 useful stays at 0.90, verify_release says READY, and the change ships. In the other direction, a real improvement can be invisible because the baseline is already at the ceiling.
- **Fix:** Add the word-overlap baseline (and BM25) as fixed rows in every eval summary, and report the app's score as a margin over the baseline. Raise the bar for 'useful': for example, require shared lemma ids (v5) or overlap of 0.5 or more. Stop counting one-letter tokens such as n, t, m, w, s, r. Report exact and near-exact (0.8 or more) hits next to 'useful'.

### A24. [medium] The 'held-out' reading-model and segmentation scores use a lexicon built from the test sentences themselves (Ramses)
`scripts/run_reading_model_eval.py:118` · tests-eval · confirmed

- **What happens:** run_reading_model_eval.py reports a high 'acc_lexicon' and better coverage of unseen groups. That looks like evidence that the lexicon generalises. In fact, for Ramses rows the lexicon is reading back the counts of the test sentence itself, and any claim like 'groups never seen in training are read correctly' is inflated.
- **Fix:** Report lexicon-assisted accuracy separately for each source, and leave Ramses and AES rows out of the test split when the lexicon is on. Better: hold out whole texts, using Rosmorduc's official split for Ramses, and rebuild a lexicon variant without those texts. Until then, do not quote the lexicon-on numbers as held-out results.

### A25. [medium] There is no untouched test set: the 'held-out' set was used to pick configurations, and the release gate runs on the development set
`data/benchmarks/release_baseline.json:3` · tests-eval · confirmed

- **What happens:** A harmless change flips one borderline v4 query (margins of 0.005 are documented): 0.90 becomes 0.85 and the release is blocked. Meanwhile, a change that overfits to the 40 queries everyone has studied passes the gate and still looks validated on the 'held-out' set.
- **Fix:** Freeze a new, larger test set that nobody inspects (100+ queries, twin-guarded as described above) and touch it only for release reports. Treat v4 and the 2026-09-05 set as development sets. Set the floor with a confidence interval, or as an allowed number of lost queries, instead of exactly the last score.

### A26. [medium] The tuning script and the main eval default to the contaminated v1 benchmark, and the tuning that set the shipped weights can't be reproduced
`scripts/tune_ranking_weights.py:40` · tests-eval · confirmed

- **What happens:** `python scripts/tune_ranking_weights.py` tunes on contaminated v1 queries (10 tune / 10 holdout), and the 'holdout' number it prints is meaningless. Nobody can re-run the tuning that produced the shipped weights or confirm its holdout gain, which was +2 queries.
- **Fix:** Make --benchmark a required argument, or default to the same file release_baseline.json names. Commit the 80-query tuning benchmark, or record in scorer.py that the weights can't be reproduced. Write outputs to a temporary directory by default, as verify_release.py does.

### A27. [medium] A non-ASCII reviewer key crashes the unlock with a traceback
